Convidar

Ana, dona do projeto, convida Bruno pela tela de Membros. O painel manda:

POST /projects/2be49b28-.../invitations
Authorization: Bearer <AccessToken da Ana>

{ "Email": "bruno@exemplo.com", "Role": "Member" }

A API confere o endereço — um só, com domínio —, que Bruno não está no time nem é dono, e que o projeto não passou do limite da hora. Grava o convite com o prazo do projeto, grava o evento, e só então põe um pedido na fila. A resposta volta sem esperar o e-mail:

{
  "Success": true,
  "Message": "Convite enviado.",
  "Data": { "PublicId": "7c1d...", "Email": "bruno@exemplo.com", "Role": "Member",
            "ExpiresAt": "2026-10-09T21:00:00Z", "EmailStatus": "Pending", ... }
}
A tela não recebe o link, nem nunca vai receber

Neste ponto o link ainda nem existe. Ele nasce no consumidor da fila, e só vai para o e-mail. Copiar o link da tela e mandar por outro canal seria cômodo, e faria o link passar por lugares que ninguém controla — e quem convida não precisa dele para nada.

O e-mail sai

O consumidor da fila pega o pedido, relê o convite, sorteia o link e reserva o envio gravando o hash dele — só um consumidor passa dessa reserva. E manda:

fila ─▶ consumidor │ ├─▶ convite ainda aberto e na fila? não ─▶ nada a fazer │ ├─▶ sorteia o link │ ├─▶ reserva: pending ─▶ sending, outro já reservou, ou a linha │ com o hash, numa gravação só mudou depois da leitura ─▶ nada a fazer │ └─▶ SMTP ├─ aceito ─▶ sent (só se continua sending, com o hash deste envio) └─ falhou ─▶ failed, e o motivo no log

O e-mail diz quem convidou, o projeto, o papel e o prazo, e traz o link:

http://localhost:5173/invite#t=Q2h2xL...

Enquanto isso, a tela de Membros relê a lista a cada dois segundos, por até meio minuto, e a linha do convite passa de "Enviando o e-mail…" para "E-mail enviado". Se não saiu, a linha diz "O e-mail não saiu", e Reenviar tenta de novo — com link novo e prazo novo. Reenviar vale em qualquer situação, inclusive com o e-mail ainda saindo: o link do envio em curso deixa de valer, e o que chega por último é o que abre.

Por que o link vem depois do #

O que vem depois do # não é mandado a servidor nenhum quando o navegador abre a página: nem ao que serve o painel, nem a um proxy no caminho, nem ao log de acesso de nenhum deles. O painel lê o link no navegador, e manda à API no corpo do pedido.

Bruno abre o link

Sem sessão, o painel mostra a entrada com Google no mesmo endereço, com um aviso de que ali há um convite — e o # sobrevive ao login. Já logado, o painel pergunta:

POST /invitations/preview
Authorization: Bearer <AccessToken do Bruno>

{ "Token": "Q2h2xL..." }
{
  "Data": { "Status": "Valid", "ProjectPublicId": "2be49b28-...", "ProjectName": "Loja Online",
            "InvitedByName": "Ana", "Role": "Member", "ExpiresAt": "2026-10-09T21:00:00Z",
            "InvitedEmailHint": null }
}

Se Bruno estivesse logado com outra conta Google, a resposta seria WrongAccount, com só a pista b•••@exemplo.com e nada do projeto, e o painel ofereceria sair e entrar com a conta certa. Com o endereço certo e ainda não confirmado pelo Google, EmailNotVerified.

Bruno aceita

POST /invitations/accept
{ "Token": "Q2h2xL..." }
{
  "Success": true,
  "Message": "Você entrou no time.",
  "Data": { "ProjectPublicId": "2be49b28-...", "ProjectName": "Loja Online" }
}

Nasce a linha de Bruno em project_members, como membro; o convite fecha como aceito e sai da lista de Ana. O painel recarrega a lista de projetos — a anterior ainda não tinha este — e abre o projeto. O acesso vale a partir dali: a requisição seguinte já lê o projeto novo do banco.

Ter o link não basta

O aceite confere, de novo, o que a prévia conferiu: a conta da sessão é a do endereço convidado, e o Google confirmou esse endereço. Um e-mail encaminhado não leva ninguém para dentro do projeto — leva só a pista de para quem o convite era.

Depois

Na tela de Membros, Ana muda o papel de Bruno, ou o tira do time — o acesso dele acaba na requisição seguinte, e o que ele escreveu nos relatos continua com o nome dele. Bruno, como membro, vê a mesma lista, sem convidar, sem mudar papel e sem tirar ninguém — a não ser ele mesmo: na própria linha, Sair do time pede confirmação e o leva de volta à lista de projetos.

DELETE /projects/2be49b28-.../members/{membro}

A rota aceita qualquer pessoa do time quando a linha é a dela; tirar outra pessoa continua só de quem administra (403 para o membro), e o dono não sai do próprio projeto (409). Quem administra e se rebaixa a membro também confirma antes — "Deixar de administrar este projeto?" —, porque não consegue desfazer sozinho.
