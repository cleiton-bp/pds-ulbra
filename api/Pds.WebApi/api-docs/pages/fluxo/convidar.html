Convidar alguém para o time

Ana convida Bruno, ele aceita pelo link do e-mail, e já está dentro.

Em resumo
  • O convite responde na hora; o e-mail sai depois, pela fila.
  • O link só existe no e-mail, nunca na tela de quem convida.
  • Só entra quem estiver logado com o Google do endereço convidado.

Convidar

Na tela de Membros, Ana convida Bruno:

POST /projects/2be49b28-.../invitations
Authorization: Bearer <AccessToken da Ana>

{ "Email": "bruno@exemplo.com", "Role": "Member" }

A API confere o endereço, o time e o limite da hora, grava o convite e o evento, põe um pedido na fila e responde sem esperar o e-mail:

{
  "Success": true,
  "Message": "Convite enviado.",
  "Data": { "PublicId": "7c1d...", "Email": "bruno@exemplo.com", "Role": "Member",
            "ExpiresAt": "2026-10-09T21:00:00Z", "EmailStatus": "Pending", ... }
}
A tela nunca recebe o link

Ele nasce no consumidor da fila e vai só para o e-mail. Assim não passa por canais que ninguém controla.

O e-mail sai

O consumidor relê o convite, sorteia o link e reserva o envio gravando o hash. Só um consumidor passa da reserva:

fila ─▶ consumidor │ ├─▶ convite ainda aberto e na fila? não ─▶ nada a fazer │ ├─▶ sorteia o link │ ├─▶ reserva: pending ─▶ sending, outro já reservou, ou a linha │ com o hash, numa gravação só mudou depois da leitura ─▶ nada a fazer │ └─▶ SMTP ├─ aceito ─▶ sent (só se continua sending, com o hash deste envio) └─ falhou ─▶ failed, e o motivo no log

O e-mail diz quem convidou, o projeto, o papel e o prazo, e traz o link:

http://localhost:5173/invite#t=Q2h2xL...
  • A tela de Membros relê a lista por até meio minuto, até mostrar "Enviado" ou "Não saiu". Passado esse tempo, a linha diz "Ainda na fila", com Atualizar.
  • Reenviar gera link e prazo novos; só o último abre.
  • O que vem depois do # não vai a servidor nem a log. O painel lê no navegador e manda no corpo.

Bruno abre o link

Sem sessão, aparece a entrada com Google no mesmo endereço, e o # sobrevive ao login. Já logado, o painel pergunta:

POST /invitations/preview
Authorization: Bearer <AccessToken do Bruno>

{ "Token": "Q2h2xL..." }
{
  "Data": { "Status": "Valid", "ProjectPublicId": "2be49b28-...", "ProjectName": "Loja Online",
            "InvitedByName": "Ana", "Role": "Member", "ExpiresAt": "2026-10-09T21:00:00Z",
            "InvitedEmailHint": null }
}
  • Com outra conta Google: WrongAccount, só com a pista b•••@exemplo.com e nada do projeto. O painel oferece trocar de conta.
  • Com o endereço certo, mas não confirmado pelo Google: EmailNotVerified.

Bruno aceita

POST /invitations/accept
{ "Token": "Q2h2xL..." }
{
  "Success": true,
  "Message": "Você entrou no time.",
  "Data": { "ProjectPublicId": "2be49b28-...", "ProjectName": "Loja Online" }
}
  1. Nasce a linha de Bruno em project_members, como membro.
  2. O convite fecha como aceito e sai da lista de Ana.
  3. O painel recarrega a lista de projetos e abre o novo. O acesso vale já na requisição seguinte.

O aceite confere tudo de novo: a conta da sessão precisa ser a do endereço convidado, confirmado pelo Google. Um e-mail encaminhado não leva ninguém para dentro.

Depois

DELETE /projects/2be49b28-.../members/{membro}
  • Quem administra muda o papel ou tira alguém (403 para o membro). O acesso acaba na hora; o que a pessoa escreveu fica.
  • O membro pode Sair do time na própria linha, com confirmação. O dono não sai (409).
  • Rebaixar a si mesmo pede confirmação ("Deixar de administrar este projeto?").
