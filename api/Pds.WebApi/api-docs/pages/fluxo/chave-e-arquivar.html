Gerar a chave secreta

O projeto nasce só com a chave pública. A secreta, para quem integra pelo servidor, nasce sob pedido: em Chaves → Integração avançada, Gerar chave secreta.

POST /projects/2be49b28-.../keys/secret
{
  "Success": true,
  "Message": "Chave secreta gerada. Ela não será exibida de novo.",
  "Data": { "PublicId": "4d0e...", "Value": "sk_EXEMPLO2...", "Prefix": "sk_EXEMPLO2",
            "CreatedAt": "2026-10-07T14:02:11Z" }
}

É a única vez que o valor existe fora do servidor: o banco guarda só o hash, e nenhuma rota consegue revelá-lo de novo. A tela mostra a chave para copiar e avisa antes de a pessoa sair dali.

Trocar a chave secreta

Com uma secreta valendo, a mesma rota (Gerar nova chave, na tela) revoga a anterior e põe uma nova no lugar, com o valor devolvido uma vez. Listando de novo, aparecem as três linhas:

Secret sk_EXEMPLO2 ativa (a nova) Public pk_EXEMPLO1 ativa Secret sk_EXEMPLO1 revogada (fica como histórico)
Trocar quebra as integrações que usam a chave antiga

É imediato e não tem desfazer. A anterior não é apagada porque o histórico de quando cada chave valeu é o que permite investigar um incidente depois.

Arquivar

PATCH /projects/2be49b28-...
{ "Status": "Archived" }

O que não vier no corpo fica como está. Arquivar não apaga nada: o projeto continua visível e consultável, só para de aceitar coisa nova. Renomear e arquivar ficam na tela Projeto, o arquivar numa seção no fim dela; os domínios têm tela própria.

Permitir ou bloquear um domínio

A tela Domínios, na área O seu sistema, começa pelo que espera decisão: Aguardando liberação, os relatos que chegaram de um domínio que ainda não está entre os autorizados; com quantos e o mais novo quando. Quem relatou não percebeu nada (tem protocolo e acompanha como sempre); o time não vê esses relatos em lugar nenhum até decidir. O sino avisa quem administra uma vez por domínio novo: "loja.com mandou um relato: permitir ou bloquear?", e o aviso leva até aqui.

GET  /projects/2be49b28-.../origins/pending
POST /projects/2be49b28-.../origins          { "Domain": "loja.com", "AllowsSubdomains": false }

Permitir põe o domínio na lista de autorizados, e os relatos retidos dele entram no topo do quadro, como relatos novos. Bloquear os apaga de vez, nunca foram aceitos. O relato que chegou sem dizer de que domínio veio tem a linha dele, com Liberar e Apagar de vez só para ele (origins/pending/release e /delete). O relato de teste do próprio painel nunca espera.

Depois vem o que já aconteceu: Domínios que mandaram relatos, com quantos, o último quando e a situação de cada um; autorizado, bloqueado, ou fora da lista (o próximo relato de lá espera liberação). Quem vê ali um domínio que não é seu clica em Bloquear, e confirma. O domínio coberto pelo bloqueio de outra linha (app.loja.com, com *.loja.com bloqueado) não tem Permitir: autorizar não mudaria nada (a API recusa com 409), e o botão passa a ser Desbloquear *.loja.com, que confirma antes, como na lista de bloqueados.

POST /projects/2be49b28-.../origins/blocked
{ "Domain": "copia-da-loja.com", "IncludesSubdomains": false }

Vale na hora: o próximo relato de lá é recusado e a ferramenta deixa de abrir. Os retidos de lá saem de vez, e os cards que já tinham entrado ficam marcados com Origem bloqueada, na lista, no quadro e no card aberto, e em Bloqueados a linha diz quantos: Revisar na lista abre a tela de Trabalho só com eles; Manter tira a marca de todos; Apagar de vez pergunta antes; diz quantos, diz que não tem volta e só libera depois de escrever o domínio ou "apagar". Na lista, a mesma decisão vale para os cards marcados da seleção, na barra do lote.

A lista de autorizados fica na mesma área, e aceita localhost:3000 (a porta faz parte) e *.loja.com para os subdomínios. Ela começa vazia: todo domínio novo passa uma vez por "Aguardando liberação". Permitir um bloqueado tira o bloqueio e autoriza; para só tirar o bloqueio, há Desbloquear, e o próximo relato de lá espera liberação.
