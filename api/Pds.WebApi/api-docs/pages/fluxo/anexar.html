Imagens e arquivos no relato

Três passos para anexar, e o arquivo nunca passa pela API.

Em resumo
  • Quem anexa é quem relatou, sempre depois do texto, com o protocolo e o token.
  • A API assina a permissão e confere o arquivo; os bytes vão do navegador direto ao armazenamento.
  • Os links de leitura são gerados a cada pedido, valem minutos e nunca são guardados.

Anexar

  1. Peça a permissão com o protocolo e o token. A API grava o anexo pendente e devolve um formulário assinado.
  2. O navegador envia o arquivo direto ao armazenamento, que recusa o que foge da assinatura.
  3. Confirme. A API lê o começo do arquivo, copia para media/ e conta a cota de novo.
o quadro já mandou o texto: tem o protocolo e o token na mão ↓ POST /public/reports/attachments { TrackingCode, Token, Kind, ContentType, SizeBytes, FileName, ... } ↓ a porta do link aceita → há armazenamento? o projeto aceita? o envio está aberto? cabe mais um? ↓ grava o anexo pendente, com um nome sorteado: uploads/<projeto>/<guid> ↓ devolve o formulário assinado: e o da miniatura, quando há: que vale 2 minutos para começar ↓ o navegador faz o POST do formulário direto ao armazenamento ↓ o armazenamento recusa o que foge da assinatura: tipo exato, de 1 byte até o teto, e no arquivo que não é imagem, Content-Disposition: attachment ↓ POST /public/reports/attachments/confirm { TrackingCode, Token, AttachmentPublicId } ↓ lê o primeiro 1 KB e o ETag → os bytes são do formato? o tipo gravado é o pedido? ↓ copia uploads/ → media/ exigindo o mesmo ETag ↓ trava a cota do relato → conta de novo → confere a regra do projeto de novo ┌──────────────────┴──────────────────┐ aceito recusado ↓ ↓ confirmado, apontando para media/ descartado no banco a cópia de envio sai do balde e os arquivos apagados do balde

Cada permissão é espaço pago no balde, por isso nada é assinado sem protocolo e token. A assinatura garante o rótulo, e a confirmação garante o conteúdo.

O que a confirmação confere
  • A marca do PNG, do JPEG e do WebP.
  • %PDF- no primeiro quilobyte.
  • Texto sem byte zero, com no máximo 2% de caracteres de controle e sem a marca do zip.
  • A marca do zip no .xlsx e no .docx; no .ods e no .odt, também o tipo que o arquivo declara dentro.
  • O tipo que o armazenamento gravou, para não depender de todo provedor aplicar a assinatura.

A permissão ainda vale minutos depois de usada, por isso o aceito vai de uploads/ para media/, exigindo o mesmo ETag. Se mudou no meio, dá 400 ("mudou depois de conferido").

A confirmação conta a cota de novo, travada, e confere a regra do projeto outra vez.

As recusas

  • 409: tentar de novo não muda (desligado, formato, tamanho, envio cheio ou vencido, sem armazenamento). A tela diz "não enviado".
  • 400: pedido mal formado, ou arquivo que não chegou ou mudou.
  • 200 ao confirmar de novo o mesmo anexo, para não duplicar.

O aceito só sai do balde quando o relato é apagado de vez (domínio bloqueado, retido apagado ou conta excluída); o recusado e as sobras são apagados, e o resto em uploads/ vence sozinho. Quanto tempo a mídia fica guardada é Adiado.

Os prazos

  • O envio: 15 minutos depois do texto ou do último arquivo do mesmo envio, com teto de 1 hora depois do texto.
  • A permissão: 1 hora para ser confirmada.
  • O formulário: 2 minutos para o envio começar (MEDIA_STORAGE_UPLOAD_URL_MINUTES).

Ler de volta

a página de quem relatou → POST /public/reports/tracking/attachments { TrackingCode, Token } pelo código pessoal → POST /public/reports/by-code/attachments { Key, Code, TrackingCode } pela identidade do sistema → POST /public/reports/by-identity/attachments { Key, IdentityToken, TrackingCode } o painel → GET /projects/{id}/reports/{id}/attachments (com sessão) ↓ a porta aceita → só então assina: um link por arquivo e um por miniatura, de 5 minutos (o de um vídeo antigo, que é lido em pedaços enquanto toca, 15) ↓ responde com Cache-Control: no-store, e ExpiresAt = o primeiro vencimento dos links ↓ a galeria pede a lista de novo 30 s antes de ExpiresAt ↓ a API fora do ar: a espera dobra a cada pedido, de 30 s até 5 min a recusa definitiva (sem armazenamento, relato que não abre): vira falha, e os pedidos param

A leitura é um POST porque o token na URL iria para o log e o Referer. O que não é imagem sempre é baixado, fora do painel como anexo.<extensão>. Detalhes em Os anexos.

O mesmo, na resposta e na reabertura

São três envios, cada um com a sua cota por categoria: a criação, a resposta a um pedido de informação e a reabertura. A sequência é a mesma, só muda uma bandeira no pedido de permissão.

POST /public/reports/reply → depois, attachments com ForReply POST /public/reports/reopen → depois, attachments com ForReopen ↓ o servidor acha a resposta, ou a reabertura, que acabou de acontecer: o navegador nunca diz qual ↓ os 15 minutos contam dela, e a cota é dela
  • A página de quem relatou não tem a chave pública, então pergunta o que dá para anexar em POST /public/reports/tracking/media-settings, com o protocolo e o token.
  • O projeto escolhe à parte se aceita anexo na resposta e na reabertura.
  • As duas bandeiras juntas dão 400: um arquivo vai com um envio só.

Cada arquivo aparece embaixo de onde veio. Quem volta pelo código pessoal ou pela identidade vê, mas não anexa.
