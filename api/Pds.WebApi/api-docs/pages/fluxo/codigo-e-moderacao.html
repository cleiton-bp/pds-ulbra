Quem relatou volta pelo código

No modo código pessoal, a confirmação entrega uma terceira coisa além do protocolo e do link: um código que vale para todos os relatos daquela pessoa naquele projeto. Quem já tinha um manda junto do relato novo, e os dois ficam na mesma lista; quem não tinha recebe o dele na resposta. Código desconhecido não é recusado — vira um código novo.

a pessoa digita o codigo no quadro, num navegador qualquer ↓ POST /public/reports/by-code { Key, Code } ↓ codigo em branco, desconhecido, ou projeto que nao usa o modo → lista vazia, e nao 404 ↓ devolve ate 50 relatos, sem o token de nenhum ↓ a pessoa escolhe um → POST /public/reports/by-code/open { Key, Code, TrackingCode } ↓ grava "visualizado" com by: reporter_code → a mesma visao publica do link, com as acoes desligadas ↓ POST /public/reports/by-code/attachments { Key, Code, TrackingCode } → os arquivos, so para ler
O código prova que o relato é dela; o link é que dá poder sobre ele

A lista não carrega o token de cada relato — embutir aqui faria doze símbolos valerem tanto quanto todos os links somados. E abrir pelo código lê, e não age: confirmar, reabrir, responder e anexar só aceitam o token do link. tracking_code_can_act segue gravado, e a API o ignora até essas rotas aceitarem o código — o que é Adiado.

Ver a lista não grava visualização; abrir um relato grava, com by: reporter_code na carga — é o que distingue, na contagem, quem voltou pela lista de quem voltou pelo link.

Os arquivos também se leem pelo código. Quem abriu o relato num navegador novo, sem o link, vê os prints que mandou ao relatar, ao responder e ao reabrir, cada um no seu lugar. A rota passa pela mesma porta de by-code/open — chave pública, código e protocolo, com a mesma recusa única para todos os enganos — e devolve a mesma lista que o link devolve: links assinados de minutos, Cache-Control: no-store, e sem o nome original dos arquivos.

Ler os arquivos não grava visualização. Quem grava é a abertura do relato, que vem antes; ler os arquivos dele não é outra leitura do relato.

Quem relatou volta pela identidade do seu sistema

No modo identidade do seu sistema, a pessoa não guarda código nenhum: quem diz quem ela é é o site do cliente. O servidor dele assina um crachá — um JWT ES256 dedicado, com sub, aud igual à chave pública do projeto e validade curta — e o põe em data-identity, no <script> do carregador; o carregador o lê a cada abertura, e o quadro o manda no envio, no corpo de POST /public/reports. A linha dela em reporter_codes nasce no primeiro relato, com o hash do sub e um código sorteado que ninguém vê; a confirmação diz se o relato ficou ligado a ela (Identified).

o site poe o cracha em data-identity; o carregador o le a cada abertura e o quadro o manda ↓ POST /public/reports/by-identity { Key, IdentityToken } ↓ cracha que nao confere, pessoa que nunca relatou aqui, ou projeto fora do modo → lista vazia, e nao 404 ↓ devolve ate 50 relatos, sem o token de nenhum — sem campo de codigo: a lista carrega sozinha ↓ a pessoa escolhe um → POST /public/reports/by-identity/open { Key, IdentityToken, TrackingCode } ↓ grava "visualizado" com by: inherited_identity → a mesma visao publica do link, com as acoes desligadas ↓ POST /public/reports/by-identity/attachments { Key, IdentityToken, TrackingCode } → os arquivos, so para ler

As três rotas são o espelho das do código, com o crachá no lugar dele. A lista responde vazia para o crachá que não confere, para a pessoa que nunca relatou aqui e para o projeto fora do modo — dizer qual dos três falhou contaria a configuração do cliente, ou algo sobre outra pessoa. Abrir e ler os arquivos têm uma recusa só, a mesma de by-code/open: crachá em branco ou que não confere, projeto fora do modo, protocolo que não existe e protocolo de outra pessoa recebem a mesma mensagem.

O crachá lê, e não age. Ele prova que o relato é dela; o link é que dá poder sobre ele — confirmar, reabrir, responder e anexar continuam pedindo o token. Ver a lista não grava visualização; abrir um relato grava, com by: inherited_identity na carga; ler os arquivos não grava de novo. "Abrir" leva à página de acompanhamento com o crachá no fragmento do endereço (#i=), que o navegador nunca envia a servidor nenhum — e lá os arquivos vêm de by-identity/attachments.

Sem crachá, o projeto decide: de fábrica o relato entra como protocolo, sem identidade, e a confirmação avisa que o link é a única forma de voltar; com "exigir o crachá" ligado, o quadro pede para entrar na conta antes de a pessoa escrever, e o envio sem crachá é recusado (401). O que a API confere no crachá está em Rotas públicas.

O time libera um relato para o público

Com o projeto num nível público, o que a ferramenta mostra a qualquer visitante é só o que passou pela fila. Todo relato nasce pendente:

GET /projects/{id}/reports/moderation → 25 pendentes, do mais antigo para o mais novo, e o cursor ↓ cada linha traz o texto inteiro e o que a varredura achou, com a amostra mascarada ↓ PUT .../reports/{id}/moderation { Decision: Approved | Rejected, From: Pending } ↓ outra pessoa decidiu antes? → 409, e nada muda ↓ grava report_published ou report_moderation_rejected, com quem decidiu ↓ GET /public/reports/published?key=... → os liberados, sem protocolo, sem identificador e sem anexo
Liberar não publica sozinho

São duas condições: o projeto num nível público e o relato liberado. Um relato liberado em projeto privado continua invisível — e é por isso que marcar o projeto como público depois não publica o histórico inteiro.

Recusar não apaga nem encerra: o relato continua no painel, no ciclo, e quem escreveu continua acompanhando pelo link. Voltar para pendente não existe, porque alguém olhou.

A lista pública é só texto

Os arquivos de um relato liberado não saem na lista pública: ela mostra o texto e o andamento de cada um, e mais nada. A lista com as imagens, e a página pública de um relato aprovado, são Adiado.

Em projeto privado, a tela de Moderação diz isso numa faixa no topo — "Este projeto é privado: nada daqui aparece para o público." —, e a aba Esperando não conta: a fila só importa quando o projeto abre os relatos ao público, na tela Quem relata.

A tela é uma caixa de entrada: a lista compacta para achar, o relato inteiro ao lado para ler e decidir, com o teclado (J/K andam, L libera, N não publica, X seleciona) e a decisão em lote. A fila vem 25 por vez, dos mais antigos, e o resto pelo cursor; as abas contam quantos há em cada uma. Decidir tira o relato da lista ali mesmo, sem reler a fila. E a varredura não fura a ordem — dar prioridade ao que ela marcou seria deixar o detector decidir a fila, que é a mesma autoridade que ele não tem para bloquear.

Liberados e Não publicáveis são histórico, e vêm da decisão mais recente para a mais antiga: quem liberou por engano acha o relato no topo e o tira do público. A tela ouve os avisos de card do tempo real só para recontar as abas, e diz "N novos — mostrar" em vez de mudar a lista debaixo de quem está lendo.
