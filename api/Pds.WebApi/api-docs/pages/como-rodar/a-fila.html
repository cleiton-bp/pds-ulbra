A fila

Opcional. Ela existe para dois prazos: a espera entre o time mover o relato e quem relatou ver, e o encerramento de um pedido de informação sem resposta. Sem RABBITMQ_URL, a API sobe normalmente: a espera fica indisponível — a tela de Ciclo recusa ligá-la e diz por quê —, e o pedido de informação continua funcionando, mas o prazo dele não encerra nada sozinho. Sem fila não há consumidor, e sem consumidor não há nem a varredura da subida: o pedido fica aberto até quem relatou responder ou o time agir.

Ao contrário do banco, aqui há serviço no docker-compose.yml, e o motivo é o inverso: o broker é local e descartável, e não há dado de ninguém dentro dele.

cd api
docker compose up -d rabbitmq
container pds-rabbitmq imagem pds-rabbitmq:dev (construida de api/rabbitmq/Dockerfile) volume pds-rabbitmq-data porta 5672 AMQP 15672 painel de administracao (pds / pds)

E a variável, apontando para ele:

RABBITMQ_URL=amqp://pds:pds@localhost:5672/

O que mais o compose sobe

São quatro serviços. A fila e o armazenamento sobem sozinhos; o minio-init precisa do armazenamento no ar, e a API, dos três:

rabbitmq a fila docker compose up -d rabbitmq minio o armazenamento dos anexos docker compose up -d minio minio-init minio-init cria o balde, privado, e sai api a própria API, na 5080 docker compose up -d --build (sobe tudo)

Com a API dentro do compose, ela procura a fila pelo nome do serviço — amqp://pds:pds@rabbitmq:5672/ —, e não pelo localhost que o .env.local traz para quem roda a API fora dele: ali dentro, localhost seria o próprio container da API. A variável do compose vale porque a variável real tem precedência sobre o arquivo. A API só sobe depois de a fila e o armazenamento responderem, e de o balde existir. O armazenamento tem página própria: O armazenamento.

A imagem é construída, e não baixada pronta

O Dockerfile parte de rabbitmq:3.13-management e instala o rabbitmq_delayed_message_exchange, que não vem na imagem oficial — é um plugin distribuído à parte. Sem ele, a exchange do tipo x-delayed-message não pode ser declarada e nada é agendado.

É o mesmo ponto que decide onde a fila vai rodar em produção — Adiado: a hospedagem precisa permitir instalar esse plugin, e nem toda oferta gerenciada permite.

O que está esperando na fila não é a verdade

O plugin guarda as mensagens atrasadas num banco local do nó, que não é replicado. Por isso o agendamento durável mora no PostgreSQL — reports.public_stage_due_at e report_info_requests.close_at — e a subida da aplicação varre o que venceu sem ter sido aplicado.

Consequência prática: apagar o volume do broker não perde relato nenhum. Na próxima subida, o que estava vencido é aplicado.
