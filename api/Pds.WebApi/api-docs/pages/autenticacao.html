Autenticação

Login com Google e sessão por token. Não existe senha no sistema.

Em resumo
  • Quem entra se identifica pelo Google, sem senha, e o primeiro acesso já cria a conta.
  • A sessão é um JWT de 8 horas, enviado no cabeçalho Authorization.
  • Sair encerra a sessão no servidor, em todos os aparelhos.

O caminho do login

painel API Google │ │ │ │ Sign-In no navegador ──────┼───────────────────────────▶│ │◀──────────────────────────── id_token ───────────────────│ │ │ │ │── POST /auth/google ───────▶│ │ │ { IdToken } │── confere assinatura ─────▶│ │ │◀── chaves públicas ────────│ │ │ │ │ │ sub conhecido? entra │ │ │ sub novo? cria conta │ │◀── { AccessToken, User } ───│ │

A API recebe só o token de identidade do Google, e não há client secret: ela só confere.

O que a conferência valida

Assinatura, emissor, validade e destinatário: o token precisa ser para o nosso GOOGLE_CLIENT_ID, senão um token feito para outro site entraria.

Não existe cadastro

O primeiro acesso cria conta e usuário de uma vez. A busca é pelo google_subject, nunca pelo e-mail (ver a modelagem de users).

A cada login, nome, foto e e-mail vêm do token, com email_verified. O convite depende disso, porque é aceito pelo endereço.

Quem pediu para excluir a conta e entra de novo dentro de 24 horas desfaz o pedido. Depois do prazo, a conta antiga é apagada, e o login começa uma conta nova.

A sessão

O login devolve um JWT assinado em HS256, com validade de 8 horas por padrão (JWT_EXPIRATION_HOURS). O painel manda o token no cabeçalho:

Authorization: Bearer <token>
ClaimConteúdo
uidpublic_id do usuário. É por ele que o servidor sabe quem é a pessoa.
accpublic_id da conta própria
subO mesmo public_id do usuário, no claim padrão de sujeito
jtiIdentificador do token, sorteado a cada emissão
iatQuando o token foi emitido. É por ele que sair derruba as sessões de antes
iss / aud / expEmissor, destinatário e expiração

O token leva só identificadores públicos, porque JWT é assinado e não cifrado: o id interno ficaria à vista. Custa uma busca em índice único por requisição.

Os claims que ninguém lê: sub, jti e acc

sub e jti são claims padrão, para quem depura o token com ferramenta de fora. O sub repete o uid, nunca o id interno. A sessão encerrada se reconhece pelo iat, e não pelo jti.

O acc não é lido pela API nem pelo painel, que pergunta a /me: a conta vem do banco, pelo middleware. Não passe a confiar nele.

Projetos e papel também vêm do banco a cada requisição, então quem sai do time perde o acesso na hora. Ver De onde vem o acesso.

Sem tolerância de relógio

A validação usa ClockSkew = TimeSpan.Zero. O padrão do .NET aceitaria cinco minutos a mais em toda sessão.

O bilhete do tempo real

Em WebSocket o navegador não manda cabeçalho, e o token iria no endereço, que fica em log. Por isso o tempo real usa um bilhete, pedido em POST /realtime/ticket, com um minuto de validade. Ver O tempo real.

Como o bilhete é conferido

Mesmo formato e assinatura da sessão, com outro destinatário (o da sessão com .realtime no fim), num esquema que só o hub usa. As rotas REST recusam o bilhete, e o hub recusa a sessão.

Sair

POST /auth/logout grava o instante da saída (users.sessions_revoked_at). Todo token anterior deixa de valer, em todos os aparelhos: o AccountMiddleware devolve 401 ao token com iat mais antigo.

Por que uma marca de tempo, e o que mais cai junto

Uma lista de revogados só cresceria. A marca é uma coluna, lida junto com o acesso que o middleware já busca, sem consulta a mais. Sair num aparelho encerra todos; entrar de novo traz um iat novo.

O 401 vem no envelope de sempre, e o painel descarta o token. A cada meio minuto, uma varredura fecha as conexões de tempo real de sessão encerrada ou vencida.

Proteção da rota de login

Limite de 20 requisições por minuto por IP, para ninguém martelar a rota. A proteção de verdade é o Google validar o token.

O IP atrás de um proxy

Vale o IP que TRUSTED_PROXIES deixa valer. Com a lista vazia (o padrão), o X-Forwarded-For é ignorado. Preenchida, só o proxy listado é acreditado, e só um salto: aceitar de qualquer um daria um IP novo a cada pedido.
