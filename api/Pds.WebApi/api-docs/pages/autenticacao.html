Autenticação

Login com Google, sessão por token. Não existe senha no sistema.

Quem entra no painel se identifica pelo Google. A API não guarda senha, não tem recuperação de senha e não confirma e-mail — três telas e três superfícies de ataque que simplesmente não existem.

O caminho do login

painel API Google │ │ │ │ Sign-In no navegador ──────┼───────────────────────────▶│ │◀──────────────────────────── id_token ───────────────────│ │ │ │ │── POST /auth/google ───────▶│ │ │ { IdToken } │── confere assinatura ─────▶│ │ │◀── chaves públicas ────────│ │ │ │ │ │ sub conhecido? entra │ │ │ sub novo? cria conta │ │◀── { AccessToken, User } ───│ │

O Sign-In acontece no navegador, e a API recebe apenas o token de identidade que o Google emitiu. Não há client secret aqui: a API só confere, nunca pede.

O que a conferência precisa validar

Assinatura, emissor, validade e destinatário. O destinatário é o ponto que mais se esquece: sem exigir que o token tenha sido emitido para o nosso GOOGLE_CLIENT_ID, qualquer token válido do Google, emitido para qualquer outro site, seria aceito — e entrar viraria questão de ter um token, não de ser a pessoa.

Não existe cadastro

O primeiro acesso cria conta e usuário no mesmo movimento. Uma tela a menos para quem usa e um estado a menos para o sistema: não existe "conta criada mas sem ninguém dentro".

A busca é sempre pelo google_subject, nunca pelo e-mail. O motivo está na modelagem.

A sessão

A resposta do login traz um JWT assinado em HS256, com validade de 8 horas por padrão (JWT_EXPIRATION_HOURS). O painel manda esse token no cabeçalho:

Authorization: Bearer <token>
ClaimConteúdo
uidpublic_id do usuário
accpublic_id da conta
iss / aud / expEmissor, destinatário e expiração
Por que só identificadores públicos no token

Um JWT é assinado, não cifrado: qualquer um que o tenha consegue ler o conteúdo. Colocar o id interno ali seria expor justamente o número sequencial que a modelagem faz questão de manter dentro de casa.

O preço é uma consulta por requisição para traduzir o GUID na chave interna. É uma busca em índice único, e vale a troca.

O acc não é confiado pelo servidor

A conta usada nas consultas vem sempre da linha do usuário no banco, resolvida pelo middleware — nunca do claim. O acc existe para o painel saber em qual conta está sem uma chamada extra. Quem for mexer aqui não deve passar a confiar nele.

Sem tolerância de relógio

A validação usa ClockSkew = TimeSpan.Zero. O padrão do .NET aceita cinco minutos a mais, o que na prática estende toda sessão em cinco minutos sem ninguém ter decidido isso.

Sair

POST /auth/logout responde 200 e nada mais. O token é autocontido: quem o tem continua podendo usá-lo até expirar, e não há como invalidá-lo sem manter uma lista de revogados.

Limitação conhecida

Quem descarta o token é o painel. A rota existe para haver um lugar único de "sair" e para ser onde a lista de revogados entra, no dia em que derrubar sessão de verdade for requisito.

Proteção da rota de login

Limite de 20 requisições por minuto por IP. O controle de verdade é o Google validar o token; isso apenas evita que alguém fique martelando a rota.
