Como rodar

Precisa de .NET 10. Não precisa de banco local.

Todos os comandos rodam a partir da pasta api.

cd api

cp Pds.WebApi/Environment/.env.example Pds.WebApi/Environment/.env.local
# peça os valores a quem já roda o projeto

dotnet ef database update --project Pds.Data --startup-project Pds.WebApi
dotnet run --project Pds.WebApi

A API sobe em http://localhost:5080. Esta documentação fica na raiz e o Swagger em /swagger.

Não use a 5000 no macOS

O Receptor do AirPlay ocupa a 5000 e a 7000, no curinga *. O sistema até deixa a API subir em 127.0.0.1:5000 ao lado dele, mas quem atende a conexão depende da ordem em que cada um subiu — às vezes é a API, às vezes é o AirPlay. Intermitente é pior do que quebrado.

O sintoma é HTTP 403 no navegador, com a API rodando normalmente. Para confirmar quem respondeu, olhe o cabeçalho: Server: AirTunes entrega o AirPlay.

Dividir porta pede cuidado com o cache

Aplicações na mesma porta dividem a mesma origem no navegador: o cache, o localStorage e os cookies são os mesmos para todas. O CSS e o JavaScript de um projeto podem acabar servidos no lugar dos do outro quando os caminhos coincidem — a página mostra o nome do projeto errado, com o código certo no servidor.

Por isso os nossos assets têm nome próprio (docs.css, docs.js) e são servidos com no-cache.

Variáveis de ambiente

Nenhum segredo fica no código. Em desenvolvimento vem do Environment/.env.local, que não vai para o repositório; em produção, das variáveis reais do ambiente.

Peça o .env.local, não monte o seu

O banco é compartilhado pelo grupo e a aplicação no Google está registrada uma vez só: valor inventado não faz a API subir. Peça a quem já roda o projeto, por canal privado — nunca por commit ou grupo.

O JWT_SIGNING_KEY é a exceção: cada ambiente emite e valida os próprios tokens, então essa você mesmo gera.

VariávelPara quê
DB_CONNECTION_STRINGConexão com o PostgreSQL.
JWT_SIGNING_KEYAssinatura do token. openssl rand -base64 48.
JWT_ISSUER / JWT_AUDIENCEEmissor e destinatário do token.
JWT_EXPIRATION_HOURSValidade da sessão. Padrão 8.
GOOGLE_CLIENT_IDID do cliente OAuth. Ver abaixo.
CORS_ALLOWED_ORIGINSOrigens do painel, separadas por vírgula. E também do quadro de relato — veja o aviso abaixo.
RABBITMQ_URLOpcional. amqp://usuario:senha@host:5672/. Sem ela a API sobe inteira e só a espera fica indisponível.
Variável em branco conta como ausente

É o erro de configuração mais comum: o arquivo tem a linha, então parece configurado. Uma verificação só contra nulo deixaria passar.

Nem todas falham na hora de subir

DB_CONNECTION_STRING e JWT_SIGNING_KEY são lidas ao montar as dependências, então faltando qualquer uma a API não sobe — e o motivo aparece no console.

GOOGLE_CLIENT_ID só é lida no primeiro login. Isso é proposital: permite rodar a API e abrir esta documentação enquanto o cadastro no Google Cloud não sai. O preço é que, sem ele, POST /auth/google responde 500 com a mensagem genérica — o motivo real fica no log do servidor.

O nome da variável mente sobre o alcance dela

CORS_ALLOWED_ORIGINS tem nome de painel, mas a política é aplicada ao pipeline inteiro — inclusive a public/reports. Quem chama aquela rota é a ferramenta de relato, servida da mesma origem do painel; servir o painel em outra porta faz o envio do formulário falhar com "Falha de rede", sem erro nenhum do lado do servidor. Dar política própria à rota pública é tarefa separada.

A lista de CORS vazia não libera tudo

Nenhuma origem configurada significa nenhuma origem autorizada. O padrão é fechado.

O banco

PostgreSQL hospedado, compartilhado pelo grupo. Não há banco local nem serviço de banco no docker-compose.yml — subir um ao lado seria convite a rodar migração no lugar errado sem perceber.

Duas armadilhas na string de conexão:

  • O hostname interno não serve da sua máquina. A hospedagem dá dois: o interno só resolve de dentro dela própria. De fora é preciso o externo, com domínio completo. Quando a API for publicada lá, vale trocar pelo interno, que não sai para a internet e responde mais rápido.
  • SSL Mode=Require é obrigatório. A hospedagem recusa conexão em texto claro.
O banco é compartilhado

Migração aplicada vale para todo mundo na hora. Combine com o grupo antes de rodar database update.

A fila

Opcional. Ela existe para dois prazos: a espera entre o time mover o relato e quem relatou ver, e o encerramento de um pedido de informação sem resposta. Sem RABBITMQ_URL, a API sobe normalmente e essas duas regras ficam indisponíveis — a tela de Ciclo recusa ligá-las e diz por quê.

Ao contrário do banco, aqui há serviço no docker-compose.yml, e o motivo é o inverso: o broker é local e descartável, e não há dado de ninguém dentro dele.

cd api
docker compose up -d rabbitmq
container pds-rabbitmq imagem pds-rabbitmq:dev (construida de api/rabbitmq/Dockerfile) volume pds-rabbitmq-data porta 5672 AMQP 15672 painel de administracao (pds / pds)

E a variável, apontando para ele:

RABBITMQ_URL=amqp://pds:pds@localhost:5672/
A imagem é construída, e não baixada pronta

O Dockerfile parte de rabbitmq:3.13-management e instala o rabbitmq_delayed_message_exchange, que não vem na imagem oficial — é um plugin distribuído à parte. Sem ele, a exchange do tipo x-delayed-message não pode ser declarada e nada é agendado.

É o mesmo ponto que decide onde a fila vai rodar em produção: a hospedagem precisa permitir instalar esse plugin, e nem toda oferta gerenciada permite.

O que está esperando na fila não é a verdade

O plugin guarda as mensagens atrasadas num banco local do nó, que não é replicado. Por isso o agendamento durável mora no PostgreSQL — reports.public_stage_due_at e report_info_requests.close_at — e a subida da aplicação varre o que venceu sem ter sido aplicado.

Consequência prática: apagar o volume do broker não perde relato nenhum. Na próxima subida, o que estava vencido é aplicado.

Login com Google

O GOOGLE_CLIENT_ID sai do console do Google Cloud, em APIs e serviços → Credenciais → ID do cliente OAuth, tipo aplicativo web. Em desenvolvimento funciona com localhost; para o ambiente publicado é preciso ter o domínio antes.

Não há client secret aqui: quem faz o Sign-In é o painel, no navegador, e a API apenas confere o token recebido.

Migrações

dotnet ef migrations add <Nome> --project Pds.Data --startup-project Pds.WebApi --output-dir Migrations
dotnet ef database update --project Pds.Data --startup-project Pds.WebApi

Usa o dotnet-ef global. O pacote Microsoft.EntityFrameworkCore.Tools não está no projeto de propósito: era redundante com o Design já presente na WebApi e arrastava uma dependência transitiva com vulnerabilidade conhecida.

Esta documentação

Fica em Pds.WebApi/api-docs. A pasta seria wwwroot pela convenção do ASP.NET Core; o nome foi trocado para dizer o que ela guarda, e a raiz web é apontada em Program.cs.

  • index.html — a casca: menu lateral e área de conteúdo.
  • assets/js/docs.js — o roteador. A lista ROUTES define o menu.
  • assets/css/docs.css — o estilo.
  • pages/*.html — uma página por rota.
  • assets/js/swagger-back.js — o botão de volta que aparece na barra do Swagger. É injetado na página dele pelo Startup.cs, e fecha o caminho de ida e volta entre os dois.
Os nomes dos assets não são genéricos por acaso

Eram app.js e styles.css. Nomes assim colidem com os de qualquer outro projeto na mesma origem, e o cache do navegador serve um no lugar do outro.

Para acrescentar uma seção: crie pages/nome.html e adicione a entrada em ROUTES. A ordem da lista é a ordem do menu e a do anterior/próximo no rodapé.

Editar uma página não pede rebuild

Com dotnet run, os arquivos são servidos direto da pasta do projeto: salvar e atualizar o navegador basta. Só mexer em ROUTES pede recarregar a página inteira, porque o menu é montado uma vez.

Cada página é só um fragmento de HTML, sem <head> nem <body> — o primeiro <h2> vira o título e o <p class="lead"> seguinte, o subtítulo. Para os blocos destacados existem três estilos: note why para o porquê de uma decisão, note warn para armadilha, e note todo para o que ainda falta.
