Fluxo rápido

Do zero ao primeiro relato chegando.

1. Entrar

O painel faz o Sign-In com o Google e manda o token recebido:

POST /auth/google
{ "IdToken": "<id_token do Google>" }

Resposta:

{
  "Success": true,
  "Data": {
    "AccessToken": "eyJhbGciOi...",
    "ExpiresAt": "2026-08-18T06:13:43Z",
    "User": {
      "PublicId": "aaaaaaaa-...",
      "Name": "Ana",
      "Account": { "PublicId": "11111111-...", "Name": "Conta de Ana" }
    }
  }
}

Se for o primeiro acesso, a conta e o usuário nasceram nesta chamada. Não há tela de cadastro.

2. Criar o projeto

POST /projects
Authorization: Bearer <AccessToken>

{ "Name": "Loja Online" }

A resposta traz o projeto e as duas chaves — e é a única vez que o valor da chave secreta existe fora do servidor:

{
  "Success": true,
  "Message": "Projeto criado. Guarde a chave secreta: ela nao sera exibida de novo.",
  "Data": {
    "Project":   { "PublicId": "2be49b28-...", "Name": "Loja Online", "Status": "Active" },
    "PublicKey": { "Type": "Public", "Value": "pk_1R0KtQwzLCVyS4RKh-8CqcHy" },
    "SecretKey": { "Value": "sk_17QxAnh7pQ1raP8J1RtxgWOn0OL6Zx_S2voTo-8TJW4",
                   "Prefix": "sk_17QxAnh7" }
  }
}
Por que as chaves nascem junto com o projeto

Sem elas o projeto não serve para nada. Obrigar a um segundo passo só cria a chance de esquecer e descobrir depois, na hora de integrar.

Projeto, chave pública e chave secreta entram numa gravação só: ou tudo entra, ou nada entra. Não existe projeto sem chave.

3. Conferir as chaves

GET /projects/2be49b28-.../keys
{
  "Data": [
    { "Type": "Public", "Value": "pk_1R0Kt...", "Prefix": "pk_1R0KtQwz", "IsActive": true },
    { "Type": "Secret", "Value": null,          "Prefix": "sk_17QxAnh7", "IsActive": true }
  ],
  "Total": 2
}

A secreta vem com Value: null. Não é a tela que esconde — o banco não tem o valor dela para devolver.

4. O primeiro relato chegando

Com a chave pública em mãos, o site do cliente cola uma linha. É a única coisa nossa que fica no HTML dele:

<script src="https://.../v1/pds.js" data-key="pk_1R0KtQwz" defer></script>

O que acontece daí em diante não passa por sessão nenhuma:

o script cria um iframe apontando para o NOSSO domínio — invisível ↓ a página manda a chave, a rota e a origem por postMessage ↓ GET /public/widget-settings → este endereço pode abrir? como o cliente quer o quadro? ↓ o quadro pede para aparecer, e só então o gatilho surge no canto ↓ quem preenche o formulário está dentro do iframe, na nossa origem ↓ POST /public/reports → confere o endereço de novo, protocolo + token

O formulário nunca toca a página do cliente, e a página do cliente nunca toca o formulário: são origens diferentes, e a única coisa que atravessa é o que as duas pontas conferiram.

Por que o quadro nasce invisível

O pedido para aparecer é a mesma mensagem que informa tamanho e canto, e o quadro só a manda depois de ler a configuração. Uma regra resolve quatro coisas: ele aparece já no canto certo em vez de pular de lado; a ferramenta desligada simplesmente nunca pede e nunca aparece; o rótulo do cliente não pisca, porque nada é desenhado com os padrões para ser trocado na frente de quem já estava lendo; e um quadro que não carregou some, em vez de deixar uma pílula vazia parada no site.

O preço é uma ida à rede antes do gatilho aparecer. Se essa leitura falhar, valem os padrões e a ferramenta abre assim mesmo — "não consegui saber" não pode virar "não apareço", porque é justamente quando algo quebrou que alguém precisa avisar.

Por que o relato carrega a chave no corpo, e não um cabeçalho

Não há credencial nesta requisição — a chave pública não autentica ninguém, ela só diz para qual projeto o relato vai. Tratá-la como cabeçalho de autorização convidaria o próximo leitor a achar que ela protege alguma coisa.

A origem é conferida, e continua não sendo prova

O campo Origin é declarado pela própria página que embutiu a ferramenta, e é comparado com a lista de project_origins nas duas rotas que a ferramenta usa. Projeto com a lista vazia aceita qualquer endereço, e quem não declara endereço passa.

Como quem declara é o carregador, que é código nosso, a chave copiada para outro site é pega — e é para isso que a lista serve. Quem chamar a API sem passar pela ferramenta declara o que quiser: grade de proteção, não muro. O muro é o frame-ancestors montado da mesma lista, que impede o quadro de abrir fora dela e precisa de um servidor servindo o documento do quadro — chega com o domínio próprio.

5. Quem relatou volta para olhar

A confirmação entrega duas coisas, e elas servem para coisas diferentes: o protocolo, para a pessoa dizer de qual relato está falando, e o link, que é o único jeito de reabrir o relato. O token vive no fragmento dele:

https://.../tracking.html?c=7K2M-9QXP-4TRV#t=<token>
a pessoa abre o link — a pagina le o fragmento, que nunca foi ao servidor ↓ POST /public/reports/tracking { TrackingCode, Token } ↓ acha pelo protocolo → confere o token em tempo constante ↓ grava o evento "visualizado", com origem public_page ↓ devolve so o que a propria pessoa escreveu, com Cache-Control: no-store

O que volta é um contrato próprio, e não o detalhe que o painel lê: rota, origem, contexto técnico e o nome que o cliente dá ao projeto por dentro ficam de fora. Se ele herdasse do outro, cada campo novo do painel — comentário interno, responsável, estado bruto — passaria a sair aqui sem ninguém decidir isso, e vazamento por herança não dá erro em teste nenhum.

Quem tem o link lê o relato

Isso é consequência do desenho, e não descuido: um link que exigisse senha não seria um link, e quem relata um defeito num site não tem conta em lugar nenhum. A confirmação diz isso na hora de entregar o link — "guarde para você" —, que é o que transforma a consequência em escolha de quem recebeu.

O protocolo sozinho não abre nada, e é por isso que ele pode ser lido em voz alta para o suporte.

A resposta traz a jornada, na ordem, com o passo em que o relato está e as datas em que ele chegou a cada um. As datas vêm dos eventos: um relato pode pular etapas, e marcar como percorrido tudo que está antes contaria uma história que não aconteceu.

O recorte do evento mora na consulta, e não num filtro depois

A leitura que monta o andamento traz só eventos de mudança de etapa pública. Uma leitura genérica "eventos do relato", filtrada na saída, funcionaria hoje e seria o vazamento de amanhã — bastaria acrescentar um tipo de evento e esquecer de atualizar o filtro para comentário interno sair para quem não é do time, sem erro em lugar nenhum.

É a mesma regra da lista de permissão que monta a resposta: tipo novo nasce invisível.

O que falta aqui

O limite de envio em public/reports: hoje a única rota da API com limitador é a de login, e são as rotas públicas que qualquer visitante de qualquer site alcança.

E a página que consome esta rota é uma aplicação React: o navegador baixa 80 kB comprimidos — 67 deles são o próprio React — antes de desenhar uma linha do tempo que não tem interação nenhuma. Para a tela que uma pessoa qualquer abre do telefone, renderizar no servidor custaria uma fração disso.

O sintoma foi tratado, a causa não. O tracking.html desenha um esqueleto escrito no próprio HTML, que aparece antes de qualquer script ou folha de estilo — a tela branca acabou, e custou 0,9 kB. Mas os 80 kB continuam sendo baixados, e o critério de renderizar no servidor continua aberto.

Esse esqueleto não é customizável por projeto, e não dá para ser: o arquivo é estático e igual para todos, e qual é o projeto só se descobre quando o pacote roda e pergunta à API — momento em que a espera já terminou. A versão com a cor e o texto do cliente mora no quadro, onde o carregador conhece a chave pública antes de abrir.

Regenerar a chave secreta

POST /projects/2be49b28-.../keys/secret

A anterior é revogada e uma nova nasce, com o valor devolvido uma vez. Listando de novo, aparecem as três linhas:

Secret sk_pAzFhfsQ ativa (a nova) Public pk_1R0KtQwz ativa Secret sk_17QxAnh7 revogada (fica como histórico)
Regenerar quebra as integrações que usam a chave antiga

É imediato e não tem desfazer. A anterior não é apagada porque o histórico de quando cada chave valeu é o que permite investigar um incidente depois.

Arquivar

PATCH /projects/2be49b28-...
{ "Status": "Archived" }

O que não vier no corpo fica como está. Arquivar não apaga nada: o projeto continua visível e consultável, só para de aceitar coisa nova.
