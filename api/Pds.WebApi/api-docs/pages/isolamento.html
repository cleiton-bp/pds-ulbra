Isolamento por conta

A parte do sistema onde um erro custa mais caro.

Cada conta enxerga apenas os próprios dados. Não é uma regra que cada consulta aplica: é uma propriedade do acesso a dados.

Por que não filtrar em cada consulta

Filtrar por conta em cada método funciona enquanto todo mundo lembra. Um dia alguém escreve uma consulta nova e esquece — e aqui esquecer é entregar dado de outro cliente. O filtro precisa estar onde não dá para esquecer.

Onde o filtro mora

Em DataContext, como filtro global de consulta:

modelBuilder.Entity<Project>()
    .HasQueryFilter(project =>
        project.DeletedAt == null &&
        project.AccountId == CurrentAccountId);

O EF lê CurrentAccountId a cada consulta, então o filtro acompanha a requisição. Toda leitura de projeto já nasce restrita, venha de onde vier.

As chaves chegam pela navegação

modelBuilder.Entity<ProjectKey>()
    .HasQueryFilter(key =>
        key.DeletedAt == null &&
        key.Project.DeletedAt == null &&
        key.Project.AccountId == CurrentAccountId);

A tabela project_keys não repete account_id, porque a chave não existe fora de um projeto. O preço é o filtro passar pela navegação; o ganho é não ter a mesma informação em duas tabelas podendo divergir.

project_origins segue exatamente o mesmo desenho, pelo mesmo motivo, e por isso tem um filtro próprio idêntico. Vale reparar no detalhe que engana: o filtro escrito no DataContext substitui o de exclusão lógica herdado, não soma — quem esquecer de repetir DeletedAt == null ali perde o apagado sem nenhum erro de compilação.

O relato compara coluna, e não navegação

modelBuilder.Entity<Report>()
    .HasQueryFilter(report =>
        report.DeletedAt == null &&
        report.AccountId == CurrentAccountId);

reports é a exceção deliberada ao desenho acima: ela repete account_id em vez de alcançar a conta pelo projeto. É a tabela que mais cresce e a que o painel lista o tempo todo, então o isolamento vira comparação de coluna em vez de junção em toda consulta. report_contexts volta ao padrão e chega pelo relato.

As duas consultas que atravessam o filtro

São exatamente duas em todo o sistema, e as duas são propositais.

A primeira resolve o projeto pela chave. A rota pública de relato chega sem sessão: nesse momento a conta ainda não é conhecida, e é justamente a chave pública que vai revelá-la. Com o filtro ligado, a consulta nunca acharia nada — sem sessão, CurrentAccountId é zero.

Context.ProjectKeys
    .IgnoreQueryFilters()
    .Include(key => key.Project)
    .FirstOrDefaultAsync(key =>
        key.Value == value &&
        key.Type == ProjectKeyTypeEnum.Public &&
        key.RevokedAt == null &&
        key.DeletedAt == null &&
        key.Project.DeletedAt == null);
IgnoreQueryFilters desliga os dois filtros, não só o da conta

Junto com o isolamento cai também a exclusão lógica. Por isso as duas condições que o filtro garantia estão reescritas à mão logo ali — DeletedAt == null na chave e no projeto. Retirar qualquer uma faz chave revogada ou projeto apagado voltarem a aceitar relato, e nada acusa: compila, responde 200 e grava.

É por isso que ela mora em ProjectKeyRepository, escrita uma vez, e não espalhada pelos serviços. Uma exceção que se pode apontar com o dedo é uma exceção; uma que se repete vira o novo padrão.

A segunda é a conferência de protocolo repetido, na criação do relato:

Context.Reports
    .IgnoreQueryFilters()
    .AnyAsync(report => report.TrackingCode == trackingCode);

Aqui a pergunta vale para o sistema inteiro, e não para a conta: quem digita um protocolo não sabe de qual projeto o relato é, então dois relatos de contas diferentes com o mesmo código levariam a pessoa ao lugar errado. Ela também inclui o que foi apagado — a linha some da lista, mas o papel com o protocolo continua na mão de alguém.

Atravessar o filtro para ler não é atravessar para gravar

O filtro global vale para leitura. Gravar um relato sem sessão funciona normalmente: o account_id da linha nova vem do projeto que a chave resolveu, e não da sessão que não existe.

O efeito é que o relato entra sem sessão e, a partir daí, só a conta dona o enxerga. Foi medido: com a conta dona, a consulta devolve o relato; sem sessão ou com outra conta, devolve zero.

De onde vem a conta

Do token, e só. O AccountMiddleware roda depois da autenticação, lê o uid, busca a linha do usuário e preenche o contexto da requisição.

token validado │ └─▶ uid (GUID do usuário) │ └─▶ consulta no banco ─▶ id interno do usuário id interno da conta │ └─▶ filtro global do contexto
Nenhuma rota aceita conta por parâmetro

Não há ?accountId=, nem campo de conta no corpo de nenhuma requisição. Se o cliente pudesse informar a conta, o isolamento viraria sugestão.

Sem sessão, nada volta

Sem usuário identificado, CurrentAccountId é zero, que não corresponde a nenhuma conta. O padrão é não ver nada, e não ver tudo.

Por que 404, e não 403

Pedir um projeto de outra conta responde 404 Não encontrado.

Do ponto de vista do código não há escolha: o filtro global simplesmente não devolve a linha, então para a aplicação o projeto não existe mesmo. E é também a resposta certa do ponto de vista de quem pergunta — dizer "existe, mas não é seu" já é contar que existe.

Identidade fica de fora do filtro

accounts e users não têm filtro de conta. São as tabelas consultadas no login, quando ainda não se sabe de qual conta a pessoa é — filtrá-las quebraria a única consulta que precisa acontecer antes da sessão existir.

Nenhuma rota lista usuário ou conta de forma aberta: o acesso a elas passa sempre pelo identificador que veio do token.

O que falta

O critério de pronto da etapa 1 pede um teste automatizado provando que uma conta não alcança o projeto de outra por nenhum caminho. O comportamento foi verificado à mão, mas ainda não está registrado como teste.
