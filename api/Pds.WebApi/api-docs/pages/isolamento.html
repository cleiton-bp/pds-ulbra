Isolamento por conta

A parte do sistema onde um erro custa mais caro.

Cada conta enxerga apenas os próprios dados. Não é uma regra que cada consulta aplica: é uma propriedade do acesso a dados.

Por que não filtrar em cada consulta

Filtrar por conta em cada método funciona enquanto todo mundo lembra. Um dia alguém escreve uma consulta nova e esquece — e aqui esquecer é entregar dado de outro cliente. O filtro precisa estar onde não dá para esquecer.

Onde o filtro mora

Em DataContext, como filtro global de consulta:

modelBuilder.Entity<Project>()
    .HasQueryFilter(project =>
        project.DeletedAt == null &&
        project.AccountId == CurrentAccountId);

O EF lê CurrentAccountId a cada consulta, então o filtro acompanha a requisição. Toda leitura de projeto já nasce restrita, venha de onde vier.

As chaves chegam pela navegação

modelBuilder.Entity<ProjectKey>()
    .HasQueryFilter(key =>
        key.DeletedAt == null &&
        key.Project.DeletedAt == null &&
        key.Project.AccountId == CurrentAccountId);

A tabela project_keys não repete account_id, porque a chave não existe fora de um projeto. O preço é o filtro passar pela navegação; o ganho é não ter a mesma informação em duas tabelas podendo divergir.

De onde vem a conta

Do token, e só. O AccountMiddleware roda depois da autenticação, lê o uid, busca a linha do usuário e preenche o contexto da requisição.

token validado │ └─▶ uid (GUID do usuário) │ └─▶ consulta no banco ─▶ id interno do usuário id interno da conta │ └─▶ filtro global do contexto
Nenhuma rota aceita conta por parâmetro

Não há ?accountId=, nem campo de conta no corpo de nenhuma requisição. Se o cliente pudesse informar a conta, o isolamento viraria sugestão.

Sem sessão, nada volta

Sem usuário identificado, CurrentAccountId é zero, que não corresponde a nenhuma conta. O padrão é não ver nada, e não ver tudo.

Por que 404, e não 403

Pedir um projeto de outra conta responde 404 Não encontrado.

Do ponto de vista do código não há escolha: o filtro global simplesmente não devolve a linha, então para a aplicação o projeto não existe mesmo. E é também a resposta certa do ponto de vista de quem pergunta — dizer "existe, mas não é seu" já é contar que existe.

Identidade fica de fora do filtro

accounts e users não têm filtro de conta. São as tabelas consultadas no login, quando ainda não se sabe de qual conta a pessoa é — filtrá-las quebraria a única consulta que precisa acontecer antes da sessão existir.

Nenhuma rota lista usuário ou conta de forma aberta: o acesso a elas passa sempre pelo identificador que veio do token.

O que falta

O critério de pronto da etapa 1 pede um teste automatizado provando que uma conta não alcança o projeto de outra por nenhum caminho. O comportamento foi verificado à mão, mas ainda não está registrado como teste.
