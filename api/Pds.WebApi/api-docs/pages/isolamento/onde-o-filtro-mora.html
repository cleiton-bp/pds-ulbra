Onde o filtro mora

Em DataContext, como filtro global de consulta:

modelBuilder.Entity<Project>()
    .HasQueryFilter(project =>
        project.DeletedAt == null &&
        project.AccountId == CurrentAccountId);

O EF lê CurrentAccountId a cada consulta, então o filtro acompanha a requisição. Toda leitura de projeto já nasce restrita, venha de onde vier.

As chaves chegam pela navegação

modelBuilder.Entity<ProjectKey>()
    .HasQueryFilter(key =>
        key.DeletedAt == null &&
        key.Project.DeletedAt == null &&
        key.Project.AccountId == CurrentAccountId);

A tabela project_keys não repete account_id, porque a chave não existe fora de um projeto. O preço é o filtro passar pela navegação; o ganho é não ter a mesma informação em duas tabelas podendo divergir.

project_origins, project_states, project_initial_states, project_public_stages, project_status_mappings, project_widget_settings, project_cycle_settings, project_identity_settings, project_media_settings e reporter_codes seguem exatamente o mesmo desenho, pelo mesmo motivo, e por isso cada uma tem um filtro próprio idêntico. Vale reparar no detalhe que engana: o filtro escrito no DataContext substitui o de exclusão lógica herdado, não soma — quem esquecer de repetir DeletedAt == null ali perde o apagado sem nenhum erro de compilação.

project_media_kinds chega à conta por dois saltos: o limite de cada categoria pendura na configuração de mídia, e a configuração no projeto. É o preço de o limite não pendurar direto no projeto — e vale a pena, porque sem a configuração esses números não querem dizer nada. O filtro repete a exclusão lógica dos três degraus:

modelBuilder.Entity<ProjectMediaKind>()
    .HasQueryFilter(kind =>
        kind.DeletedAt == null &&
        kind.ProjectMediaSettings.DeletedAt == null &&
        kind.ProjectMediaSettings.Project.DeletedAt == null &&
        kind.ProjectMediaSettings.Project.AccountId == CurrentAccountId);

O relato compara coluna, e não navegação

modelBuilder.Entity<Report>()
    .HasQueryFilter(report =>
        report.DeletedAt == null &&
        report.AccountId == CurrentAccountId);

reports é a exceção deliberada ao desenho acima: ela repete account_id em vez de alcançar a conta pelo projeto. É a tabela que mais cresce e a que o painel lista o tempo todo, então o isolamento vira comparação de coluna em vez de junção em toda consulta.

O que pendura no relato volta ao padrão e chega à conta por ele: report_contexts, report_internal_comments, report_public_comments, report_closures, report_info_requests e report_attachments.

O anexo chega pelo relato, e não pelo lugar onde veio. Um arquivo pode ter vindo com uma resposta ou com uma reabertura, e a linha aponta para elas — mas quem é dono dele é o relato, e é pelo relato que o filtro passa. É também esse filtro que faz o painel de uma conta nunca assinar a leitura de um arquivo de outra: o relato de fora não volta, e nenhum link chega a ser gerado.

events também compara coluna, e só a conta: evento não se apaga, então não há exclusão lógica para repetir. accounts e users ficam de fora do filtro — ver De onde vem a conta.
