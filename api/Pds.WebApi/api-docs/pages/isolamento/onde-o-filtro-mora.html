Onde o filtro mora

Em DataContext, como filtro global de consulta:

modelBuilder.Entity<Project>()
    .HasQueryFilter(project =>
        project.DeletedAt == null &&
        CurrentProjectIds.Contains(project.Id));

O EF lê CurrentProjectIds a cada consulta, então o filtro acompanha a requisição. Toda leitura de projeto já nasce restrita, venha de onde vier.

CurrentProjectIds são as chaves internas dos projetos que a pessoa da requisição enxerga — os da conta própria e os do time —, e a lista chega pronta do middleware. Por isso o filtro é comparação de coluna, sem junção com project_members, e a lista vai ao PostgreSQL como um parâmetro só, um vetor: a comparação vira = ANY(...). Sem sessão, a lista é vazia, e vazia não enxerga nada — ver De onde vem o acesso.

As chaves comparam a própria coluna

modelBuilder.Entity<ProjectKey>()
    .HasQueryFilter(key =>
        key.DeletedAt == null &&
        key.Project.DeletedAt == null &&
        CurrentProjectIds.Contains(key.ProjectId));

A tabela project_keys não repete account_id, porque a chave não existe fora de um projeto — e o acesso, que é por projeto, compara o project_id da própria linha. Só a exclusão lógica do projeto passa pela navegação. O ganho é não ter a mesma informação em duas tabelas podendo divergir.

project_members, project_origins, project_states, project_initial_states, project_public_stages, project_status_mappings, project_widget_settings, project_cycle_settings, project_identity_settings, project_media_settings e reporter_codes seguem exatamente o mesmo desenho, pelo mesmo motivo, e por isso cada uma tem um filtro próprio idêntico. Vale reparar no detalhe que engana: o filtro escrito no DataContext substitui o de exclusão lógica herdado, não soma — quem esquecer de repetir DeletedAt == null ali perde o apagado sem nenhum erro de compilação.

project_media_kinds chega ao projeto por dois saltos: o limite de cada categoria pendura na configuração de mídia, e a configuração no projeto. É o preço de o limite não pendurar direto no projeto — e vale a pena, porque sem a configuração esses números não querem dizer nada. O acesso compara o project_id da configuração, e o filtro repete a exclusão lógica dos três degraus:

modelBuilder.Entity<ProjectMediaKind>()
    .HasQueryFilter(kind =>
        kind.DeletedAt == null &&
        kind.ProjectMediaSettings.DeletedAt == null &&
        kind.ProjectMediaSettings.Project.DeletedAt == null &&
        CurrentProjectIds.Contains(kind.ProjectMediaSettings.ProjectId));

O relato compara coluna, e não navegação

modelBuilder.Entity<Report>()
    .HasQueryFilter(report =>
        report.DeletedAt == null &&
        CurrentProjectIds.Contains(report.ProjectId));

reports é a exceção ao desenho acima: não navega até o projeto para nada. É a tabela que mais cresce e a que o painel lista o tempo todo, então o acesso é comparação de coluna, sem junção em toda consulta. Ela também repete account_id, copiado do projeto, para saber de qual conta é o relato sem junção — mas não é mais por ele que o isolamento compara.

O que pendura no relato volta ao padrão e chega ao projeto por ele: report_contexts, report_internal_comments, report_public_comments, report_closures, report_info_requests e report_attachments.

O anexo chega pelo relato, e não pelo lugar onde veio. Um arquivo pode ter vindo com uma resposta ou com uma reabertura, e a linha aponta para elas — mas quem é dono dele é o relato, e é pelo relato que o filtro passa. É também esse filtro que faz o painel nunca assinar a leitura de um arquivo de projeto em que a pessoa não está: o relato de fora não volta, e nenhum link chega a ser gerado.

events também compara coluna, e só o projeto: evento não se apaga, então não há exclusão lógica para repetir. Todo evento gravado hoje nasce de um projeto; o que um dia ficar sem ele — o projeto some de verdade, e o evento fica — não aparece no painel. accounts e users ficam de fora do filtro — ver De onde vem o acesso.
