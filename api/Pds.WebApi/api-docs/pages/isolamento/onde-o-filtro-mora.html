Onde o filtro mora

Uma linha no contexto, e toda leitura já nasce restrita.

Em resumo
  • O filtro é global, no DataContext, e compara o projeto com a lista da requisição.
  • Sem sessão, a lista é vazia, e vazia não enxerga nada.
  • O relato retido fica de fora do painel pelo mesmo filtro.

O filtro do projeto

modelBuilder.Entity<Project>()
    .HasQueryFilter(project =>
        project.DeletedAt == null &&
        CurrentProjectIds.Contains(project.Id));

O EF lê CurrentProjectIds a cada consulta. A lista chega pronta do middleware (ver De onde vem o acesso).

Por isso não há junção com project_members: a lista vai ao PostgreSQL como um vetor, e a comparação vira = ANY(...).

As tabelas do projeto

modelBuilder.Entity<ProjectKey>()
    .HasQueryFilter(key =>
        key.DeletedAt == null &&
        key.Project.DeletedAt == null &&
        CurrentProjectIds.Contains(key.ProjectId));

project_keys não repete account_id: a chave não existe fora de um projeto, então o filtro compara o project_id da própria linha.

As outras tabelas com o mesmo desenho

project_members, project_invitations, project_origins, project_blocked_origins, project_states, project_priorities, project_labels, project_report_types, project_public_stages, project_status_mappings, project_widget_settings, project_cycle_settings, project_identity_settings, project_media_settings, project_report_limits, project_team_settings e reporter_codes têm, cada uma, um filtro próprio idêntico.

project_media_kinds chega ao projeto em dois saltos: o limite de cada categoria pendura na configuração de mídia, e ela no projeto. O filtro repete a exclusão lógica dos três degraus:

modelBuilder.Entity<ProjectMediaKind>()
    .HasQueryFilter(kind =>
        kind.DeletedAt == null &&
        kind.ProjectMediaSettings.DeletedAt == null &&
        kind.ProjectMediaSettings.Project.DeletedAt == null &&
        CurrentProjectIds.Contains(kind.ProjectMediaSettings.ProjectId));
O filtro do contexto substitui, e não soma

O filtro escrito no DataContext troca o de exclusão lógica herdado. Quem esquecer de repetir DeletedAt == null ali passa a ver o apagado, sem erro de compilação.

O relato compara coluna

modelBuilder.Entity<Report>()
    .HasQueryFilter(report =>
        report.DeletedAt == null &&
        report.HeldForOriginAt == null &&
        CurrentProjectIds.Contains(report.ProjectId));

reports é a tabela que mais cresce, então compara a coluna, sem junção. Ela também copia o account_id do projeto, mas o isolamento não usa esse campo.

O relato retido também fica de fora. O que chegou de um endereço não autorizado (held_for_origin_at preenchido) some de todo o painel. Só "Aguardando liberação", liberar e apagar o enxergam (ver As consultas que atravessam o filtro). As rotas públicas não passam por aqui, então quem relatou continua acompanhando.

O que pendura no relato e no trabalho do time

  • Pelo relato: report_contexts, report_labels, report_internal_comments, report_public_comments, report_closures, report_info_requests e report_attachments. A etiqueta some do card quando foi apagada, mesmo que a ligação tenha ficado.
  • O anexo é do relato, mesmo vindo com uma resposta. Por isso o painel nunca assina arquivo de projeto alheio.
  • Por coluna: card_links e notifications repetem o project_id do card, e sprints tem o seu. O vínculo some quando um dos cards foi apagado, e o aviso, quando o card dele foi. De quem é o aviso, cada leitura diz.

Os casos à parte

  • user_notification_sounds é da pessoa e vale em todos os projetos: o filtro só tira o apagado.
  • events compara só o projeto, porque evento não se apaga. Quando a exclusão da conta apaga o projeto de verdade, o evento fica com um project_id que nenhuma lista tem, e não aparece.
  • accounts e users ficam fora do filtro (ver De onde vem o acesso).
