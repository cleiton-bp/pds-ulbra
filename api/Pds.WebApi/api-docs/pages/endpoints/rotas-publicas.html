Rotas públicas

As nove que chegam sem sessão: a ferramenta no site do cliente, e quem relatou voltando pelo link ou pelo código.

MétodoRotaO que faz
POST/public/reportsSem sessão. Abre um relato; o projeto vem da chave pública do corpo.
POST/public/reports/trackingSem sessão. Abre o acompanhamento de um relato, pelo protocolo e pelo token do link.
POST/public/reports/by-codeSem sessão. Os relatos ligados a um código pessoal. Código desconhecido devolve lista vazia, e não 404.
POST/public/reports/by-code/openSem sessão. Abre um relato da lista pessoal. Lê, e só age se o projeto ligou tracking_code_can_act.
GET/public/reports/publishedSem sessão. O que já foi liberado para o público neste projeto. Projeto privado responde lista vazia, e não uma recusa.
POST/public/reports/confirmSem sessão. Quem relatou diz que resolveu, e dá a nota — ou recusa dá-la.
POST/public/reports/reopenSem sessão. Diz que não resolveu. O relato volta para a coluna que o projeto configurou.
POST/public/reports/replySem sessão. Responde ao pedido de informação. Só enquanto houver pedido aberto.
GET/public/widget-settingsSem sessão. O que o próprio quadro lê para se desenhar, pela chave pública. Recebe também o endereço da página.
Uma leitura que é POST, e por quê

POST /public/reports/tracking não cria nada — e não é um GET por duas razões. O token é um segredo, e segredo em query string entra no log de acesso do servidor, no histórico do navegador e no Referer que sai da página; no corpo, não entra em nenhum dos três. É o mesmo cuidado que põe o token no fragmento do link (#t=), que é a parte que o navegador nunca envia a servidor nenhum.

E ela não é leitura pura: grava o evento de visualização com origem public_page. O intervalo entre o relato e a primeira olhada do time mede a reação; a volta de quem relatou mede se a camada pública serve para alguma coisa. Nenhum dos dois é reconstituível depois.

A quinta rota chegou, e não coube na mesma porta

Acompanhar, confirmar, reabrir e responder levam as mesmas credenciais no corpo — protocolo e token — e as quatro entram por um único método, RequireTrackedReportAsync. Esta página dizia que conferência espalhada por quatro rotas é conferência que uma quinta vai esquecer. A quinta chegou: POST /public/reports/by-code/open.

E ela chega com outra credencial — código pessoal e protocolo, sem token nenhum. Fazê-la entrar pela porta das outras quatro significaria afrouxar a conferência delas para caber um caso que não tem token, que é o oposto do que a porta única existe para garantir. Ela tem entrada própria, com as quatro recusas possíveis colapsadas numa mensagem só.

O que as cinco compartilham é a saída: todas respondem por BuildPublicAsync, a mesma visão montada campo a campo, sem nome de quem é do time e sem o vocabulário interno das colunas. E há uma assimetria de propósito — nas quatro do link as ações chegam ligadas; na quinta, não. O código prova que o relato é dela, o link é que dá poder sobre ele, e confirmar, reabrir e responder só aparecem se o projeto tiver ligado tracking_code_can_act.

Código que existe e código que não existe respondem igual

POST /public/reports/by-code devolve lista vazia para um código desconhecido, e não 404. É a decisão central da rota. Qualquer diferença entre "não existe" e "existe e está vazio" a transformaria num oráculo, e tentar códigos até a resposta mudar é exatamente como se enumera código alheio.

Projeto que não usa este modo responde igual, pelo mesmo motivo — dizer "aqui não tem código" contaria a configuração do cliente a qualquer um que colasse a chave pública numa requisição.

Em by-code/open a mesma disciplina vira uma recusa só: código em branco, código que não existe, protocolo que não existe e protocolo que é de outra pessoa recebem a mesma mensagem. Sem a última, qualquer código válido abriria qualquer protocolo do projeto.

Uma consulta pública que é GET, e as outras não

GET /public/reports/published destoa de propósito. Nas outras consultas públicas o corpo carrega um segredo — o token do link, o código pessoal —, e segredo em query string entra no log do servidor, no histórico do navegador e no Referer.

Aqui não há segredo nenhum: a chave pública já está no código-fonte da página do cliente. Fazer POST só por simetria esconderia que esta é a única consulta pública que não identifica ninguém.

Escrever de fora só é possível quando o produto convidou

POST /public/reports/reply é recusada quando não há pedido de informação aberto, e reopen quando o projeto desligou a reabertura. A vez volta para a equipe assim que a pessoa responde.

Canal sempre aberto viraria caixa de entrada sem dono. Quem relatou escreve quando lhe perguntaram — e isso continua valendo depois de a moderação existir: a fila decide o que vira público, e não quem pode escrever.

O protocolo identifica, o token abre

A rota exige os dois, e protocolo inexistente e token errado recebem a mesma recusa 404, com a mesma mensagem. O protocolo é curto e falado de propósito — logo adivinhável —, então responder diferente contaria a quem sonda que ele acertou metade. E 404 em vez de 403 pela razão de sempre aqui: confirmar que o relato existe já é informação.

A comparação do token é em tempo constante (ProjectKeyGenerator.Matches): um == comum para no primeiro caractere diferente, e com o protocolo em mãos a diferença de tempo permitiria descobrir o token caractere a caractere.

Por que uma rota fica fora do padrão

Quarenta e cinco rotas exigem token e resolvem a conta pelo uid que vem dentro dele. As nove de /public não podem: quem chega ali é um visitante anônimo do site de um cliente, e a conta ainda não é conhecida. A credencial é a chave pública, que não autentica ninguém — ela apenas diz para qual projeto o relato vai.

Chave ausente, desconhecida, revogada ou secreta recebem a mesma recusa, com a mesma mensagem: responder "esta chave existe, mas foi revogada" contaria a quem tenta que ele acertou metade. Ver a consulta que resolve o projeto pela chave.
